# rag-lab

**在线看** → <https://hugeaaa-asd.github.io/rag-lab/>　｜　逐题对照「旧：章节路由 vs 新：小节直选」，点开即看，不用装任何东西。

一个**只为搞清楚一件事**而写的 RAG 实验仓库：当检索链路上每一环都可以换参数时，到底哪一环在真正决定效果。

语料是一本开源技术书《Hello-Agents》的全部 16 章 Markdown（切 1177 块），自建 103 题四套基准，口径是**小节级 Recall@1/@3**（`8.3.4` 这一节，不是「章」——章对了块错了不算成功）。

结论一句话：**决定效果的是「先圈对范围」，不是排序；而分级的圈范围比一次圈到底更容易犯错。**

## 快速开始

**只想核对数字**（不装依赖、不下载模型、不调 API，约 1 秒）：

```bash
git clone https://github.com/hugeAAA-asd/rag-lab.git
cd rag-lab
python reproduce.py
```

它从仓库里的候选池（`allsub_pools_*.json`）复算 ⑧ 节那张表，只用标准库——
精排分在生成候选池时就算完了，复现只是加权、去重、取前三。没装 numpy 也能跑。

**想跑完整链路**：

```bash
pip install -r requirements.txt

# 建 .env（已在 .gitignore 中，不会入库）
echo "DEEPSEEK_API_KEY=sk-xxx" > .env

# 不配 key 也能跑通检索部分
python answer.py --dry "什么是智能体？"

# 配了 key 才走完整链路（粗筛 → 改写 → 路由 → 精排 → 生成）
python answer.py "智能体怎么像插 USB-C 一样接入外部工具？"
```

首次运行会从 HuggingFace 拉取 `bge-small-zh-v1.5`（向量）和 `bge-reranker-base`（精排），之后本地缓存。国内网络如果拉不动，代码里已经 `setdefault` 了 `HF_ENDPOINT=https://hf-mirror.com`。

**想点开看**（⑪）：

```bash
python build_demo.py     # 生成静态页 demo.html，不加载模型
python api.py            # http://127.0.0.1:8000 ，带「现场试一句」
```

## 链路：七个环节，每环都可以单独换

```
corpus/*.md
   │
   ├─ build_chunks.py   按标题层级切块，代码块按函数边界再切，过滤噪声小节
   ├─ embed.py          bge-small-zh-v1.5，512 维
   ├─ eval.py           向量粗筛 → cross-encoder 精排
   ├─ rewrite.py        口语问题改写成库里的说法，改写只提名不参与排序  ← 可选
   ├─ route.py          287 个小节一次选 3 个，章节号反推，治「词不在目录里」  ← 可选
   ├─ abstain.py        扫描拒答阈值
   └─ answer.py         拼材料 → 宪法提示 → 生成，带 [n] 引用
```

后面每个环节的取舍都有独立的对照实验，不靠直觉。

### 切块为什么不用固定长度

固定窗口切会把代码拦腰截断。`build_chunks.py` 的做法是：

- 按 `##` / `###` 分层（`level` 可调），块标题拼成「二级 > 三级」
- 超过 800 字的块**按段落边界**二次拆，不按字符硬切
- 纯代码块在 `def` / `class` 处再切，并保留 ``` 围栏，保证语法完整
- 踢掉「本章小结 / 习题 / 参考文献」这类只会抢占位置的噪声小节

> 踩过的坑：1.1 节有 3 个三级标题，只按 `##` 切会让 12 个块共用同一个标题，精排时标题字面完全相同，分数挤成一团，区分度归零。这就是 `level=3` 存在的原因。

## 基准：43 道题，按题型分六类

题目全部人工编写并按答案所在节标注，分「定义 / 细节 / 分类 / 原因 / 应用 / 对比」六类，为的是知道**弱在哪类问法上**，而不只是看一个总数。

基线配置（粗筛 + 精排，无改写、无路由）的分题型成绩：

| 题型 | 题数 | Recall@1 | Recall@3 |
|---|---|---|---|
| 定义 | 14 | 0.64 | 0.86 |
| 细节 | 12 | 0.75 | 1.00 |
| 分类 | 2 | 0.50 | 1.00 |
| 原因 | 9 | 0.56 | 0.89 |
| 应用 | 4 | 0.75 | 0.75 |
| 对比 | 2 | 0.50 | 0.50 |

> 分类、对比各只有 2 题，这两个数字没有统计意义，只用来标记「这类问法还没验证」。

在这个基线上一层层叠，每一步都有独立的对照实验（见下节）：

| 配置 | Recall@1 | Recall@3 | 43 题耗时 |
|---|---|---|---|
| 基线：粗筛 + 精排 | 0.651 | 0.907 | 510s |
| + 查询改写（候选扩充） | 0.721 | **0.953** | 861s |
| + 路由加分 bonus=0.5 | **0.884 ~ 0.907** | **0.953** | 884 ~ 941s |

> 最后一行写成区间，是因为同一配置跑了两遍，@1 分别 0.884 和 0.907（差一题）。原因见 ⑥。

## 实验：改了什么，换来什么，代价是什么

每组实验都有对照，并**记录耗时**，因为只涨指标不算数，涨了多久才是决策依据。

### ① 查询改写要不要做（`rewrite.py`）

主要的失效原因是词汇鸿沟：用户问「先检索外部资料再让模型生成答案，这套做法叫什么」，书里写的是 `## 8.3 RAG系统：知识检索增强`，两边一个字都不重合，bi-encoder 给 0.790，前三都进不去。

做法是让 LLM 生成 3 条改写，连同原问题一共 4 个 query 去粗筛。

| | Recall@1 | Recall@3 | 43 题耗时 |
|---|---|---|---|
| 基线 | 0.651 | 0.907 | 510s |
| + 改写，候选扩充 | **0.721** | **0.953** | 861s |

两条设计约束，都是踩坑换来的：

**改写只提名，不参与排序。** 一开始让改写句和原问题平起平坐做 max 融合，结果改写越准越坏事——「StateGraph」「BaaS LLMOps」这些词会撞上别处「提到过」它们的块，把真正讲这一节的挤掉。8 题实测：基线 4/8、max 融合 4/8、候选扩充 6/8，而且候选扩充是基线的严格超集（救回 2 题、弄坏 0 题）。

**精排必须用原问题打分。** 粗筛要的是「相关就行」，怎么改写都可以；精排判断的是「这段能不能回答用户真正问的那个问题」，用改写句去精排等于在回答一个用户没问的问题。

### ② 去重放在粗筛前还是精排后（`exp_dedup.py`）

同一节命中多块时，是先去重还是精排完再去重。

| | Recall@1 | Recall@3 | 每题耗时 |
|---|---|---|---|
| A 去重在粗筛 | 0.706 | 0.824 | 7.7s |
| B 去重在精排后 | 0.706 | **0.941** | 12.8s |

**结论**：Recall@1 纹丝不动，Recall@3 涨 0.117，代价是每题慢 5 秒。值不值取决于场景要 @1 还是要 @3——**这个权衡本身就是结论**。

### ③ 精排时标题要不要留在文本里（`exp_title.py`）

| 配置 | Recall@1 | Recall@3 |
|---|---|---|
| 带标题（基线） | **0.651** | **0.907** |
| 去标题 PER=2 | 0.605 | 0.860 |
| 去标题 PER=3 | 0.605 | 0.884 |

**结论**：反而掉了 4.6 个点。章节标题是 strong signal，别当噪声洗掉。这条推翻了「精排只该看正文」的直觉。

### ④ 拒答阈值怎么定（`abstain.py` → 直接驱动 `answer.py`）

这是本仓库唯一一条**从实验走到代码常量**的链路。

阴性样本分三档难度：T1 完全离题、T2 同领域但书里没写、T3 书里提过名字但没有答案。

| 档 | 题数 | top1 均值 | 最高 |
|---|---|---|---|
| T1 | 3 | 0.244 | 0.570 |
| T2 | 5 | 0.342 | 0.811 |
| T3 | 4 | 0.635 | **0.969** |

正样本 top1 分布：最低 0.291 / 中位 0.970 / 95% 0.999。

以 0.05 为步长扫全程，最优阈值 **0.60**：正确拒答 8/12，误拒 1/43，总正确率 **0.909**。

这个 0.60 写进了 `answer.py` 的 `MIN_SCORE`。

### ⑤ 提问风格有多影响检索（`eval_style.py` / `eval_oral.py`）

同一考点用三种问法：**绕弯**（如「能感知环境并自主采取行动的系统是什么」）、**术语**（"ReAct"）、**极短**（单个词）。

术语档 13 题 top1 全中，分数 0.989~1.000。绕弯档多数落到第 2 名。

极短口语档是最短板：

| | Recall@1 | Recall@3 |
|---|---|---|
| 纯原问 | 0.231 | 0.538 |
| + 查询改写 | 0.385 | 0.615 |

### ⑥ 路由加分：先撞墙，再靠降 bonus 化解（`eval_combo.py` / `eval_bonus05*.log`）

⑤ 发现极短口语档是最短板。而这档的病恰好是改写治不了的：口语碎片（「怎么让它查资料」）信息量太少，LLM 推不出术语。这时候只有路由管用——把章节目录交给模型挑，靠匹配不靠推断。

先在完整 43 题上验证 bonus=1.0（路由命中的章节直接压过精排）：

| | Recall@1 | Recall@3 | 43 题耗时 |
|---|---|---|---|
| 基线（无改写无路由） | 0.651 | 0.907 | 510s |
| A 改写 | 0.721 | **0.953** | 861s |
| B 改写 + 路由 bonus=1.0 | **0.884** | 0.930 | 923s |

**@1 涨 16.3 个点，@3 反而掉 2.3 个点，还弄坏了 2 题。** 12 题改善（其中 1 题从「未进前 3」直接救回第 2 名），2 题从第 1 名掉出前 3——都是**列举 / 选型类**问题（「用什么框架来描述一个智能体的任务环境？」「阿里达摩院做的、强调工程化和高可靠的多智能体平台是哪个？」）。路由认出了「工具 / 框架」语义，把候选优先给了相关但讲的是另一件事的章节。

问题不在路由判错，在 bonus=1.0 给了它**独裁权**：路由 3 个候选全错时，精排没有否决机会。降 bonus 就是给精排留一个否决权：

| bonus | Recall@1 | Recall@3 | 43 题耗时 |
|---|---|---|---|
| 1.00 | 0.884 | 0.930 | 923s |
| **0.50**（第 1 次） | 0.884 | **0.953** | 884s |
| **0.50**（第 2 次） | **0.907** | **0.953** | 941s |

**0.50 是扫出来的，不是拍的：@1 的收益保留，@3 回到 0.953，被挤掉的题换回来了。** 当时写进了 `answer.py` 的 `ROUTE_BONUS`。

> 注：这一节是历史记录，口径是**章节级**。⑧ 之后 `ROUTE_BONUS` 改成 `[0.6, 0.2, 0.0]`、口径改成小节级，本节数字不要和 ⑧ 的表混着看。

**同时暴露了一个必须写下来的问题：同一配置跑两次，@1 是 0.884 和 0.907。** 差一题。因为路由要调 LLM，判别有非确定性，而 43 题里一题就是 2.3 个点。所以本仓库里 1~2 题的差异都不该被当成真实提升——这条比上面所有加分都重要。

### ⑦ 路由准确率就是排序的上限（`exp_route_bonus.py`）

排序再好也超不过路由选对的概率。13 题极短口语档上单独量了一次：

| | Recall@1 | Recall@3 |
|---|---|---|
| 纯原问 | 0.231 | 0.538 |
| + 查询改写 | 0.385 | 0.615 |
| + 改写 + 路由（bonus 1.0） | **0.769** | **0.923** |

路由自身：@3 命中 12/13 = 0.923，第 1 名即正确 8/13 = 0.615。

**0.923 就是这套链路在口语档的天花板**——精排再强也只能无限接近它，不可能超过。反过来说，口语档想继续往上走，唯一的路是提高路由命中率（目录切得更细、或者路由前先做一次实体识别），不是继续调精排。

bonus 单独扫（同一批 13 题）：0.30 → 0.692 / 0.846、0.60 → 0.769 / 0.846、1.00 → 0.769 / 0.923。**太低路由就白做了，太高就在长尾题上翻车**；43 题上取 0.5、13 题极短档取 1.0，说明最优 bonus 本身跟着场景走，没有全局值。

### ⑧ 从小到大：章节路由 → 小节直选（`route_allsubs` / `reproduce.py`）

⑦ 说「路由准确率就是天花板」。这一节是去顶天花板的过程，也是这个仓库**唯一一次真正的结构改动**。

**先定位：瓶颈是候选缺失，不是排序。**
第三留出集 h3 的 6 个失败里，4 个是「章节选对了、块没顶上来」。做了一次上限实验——直接告诉它正确小节号，把那些块全塞进候选池：

| 口径 | 现状 | 补齐正确小节 |
|---|---|---|
| 小节 @1 | 0.700 | **0.650** |
| 小节 @3 | 0.700 | **0.850** |

补齐后 @3 涨 0.15、@1 反而跌。原因是**按章节去重**：一章只出一个代表块，代表由章内最高分决定。块都在池里、精排也看见了，就是选不出那一个。

**第一次尝试（两级）失败了，失败得很值：**
79 章选 3 → 那 3 章的小节清单合成一张（约 12 条）→ 再选 3 个。选择准确率看着不错（首选 0.950，用正确章节做条件），但接进检索后 **43 题零收益**。两个坑：

1. 给选中的 3 个小节同样加分 = 等于没加。8.3 那题选了 `[8.3.4, 8.3.2, 8.3.1]`，整章都加了分，而 8.3.1 的块精排分本来最高，排序一动不动。**只有首位小节带信息量，后两位是模型给自己的保险丝。**
2. 更要命：h3 的 5 个失败里有 3 个是**正确章节压根没进 3 个候选**（3.2 分词、5.5 n8n 邮件、7.4 SimpleAgent）。章节选错，小节再准也只是在错的章里挑。

**结论：分级检索的前提是「上一级不漏」。漏了就是放大器，不是省时间。**

**改法：越级直选。** 把 287 个小节一次性交给模型选 3 个，章节号由小节号反推（`8.3.4` → `8.3`）。省掉一次调用，prompt 从 1200 涨到 5000 token。

| 数据集 | 题量 | 旧：章节路由 @1 | 新：小节直选 @1 | 新 @3 | 备注 |
|---|---|---|---|---|---|
| 43 开发集 | 40（有标注） | 0.900 | **0.925** | 0.950 | 主证据 |
| h1 留出 | 20 | 0.650 | **0.800** | 0.850 | 参与过 sub1 选型，偏乐观 |
| h2 留出 | 20 | 0.350 | **0.700** | 0.800 | 照它的失败补过词，偏乐观 |
| h3 干净集 | 20 | 0.700 | **0.950** | 1.000 | 唯一未污染，主证据 |

四套零退化。复现命令 `python reproduce.py`，数字由脚本从候选池复算，不要手改。

**顺手补的一个洞：NONE 出口。**
改成直选后 `picks` 由 `subs` 反推，`routed_top1` 恒为真，拒答阈值形同虚设——「推荐几家火锅店」也会被硬选一个小节。在提示词里明确允许输出 `NONE` 之后，目录外问题正常拒答，**而且准确率反而涨了（.900→.950）**：逼模型敢说「没有」，它选得更准。

**代价**：prompt 1200 → 5000 token（省掉一次调用，净成本基本持平）；每题多补 9~10 块进精排，耗时 +35%（端到端 14.4s）。

**封盘时抓到的一个 bug（值得单说）：**
`reproduce.py` 第一次跑出来，@1 全对、@3 却比实测低（h1 .850→.800、h2 .800→.750）。查下去发现是生产代码的语义错误：`confs` 是空列表时，`search_multi` 用 `confs is not None` 判断，空列表也算「有置信度」，于是 `pos >= len(confs)` 成立，**章节加分被全量清零**。而 subs 模式压根没有章节原始输出，`parse_conf("")` 返回 `[]`——「没有置信度」被当成了「置信度很低」。

@1 看不出来（小节加分已经够了），只在 @3 露头。修法是一行：`confs=... if (picks and raw_route) else None`。**这就是「数字必须由脚本算出」的理由——手抄的表不会告诉你哪一列掉了。**

**三条调参的证伪记录**（写下来是为了以后别再试）：

| 改动 | 结果 |
|---|---|
| 置信度缩放 | 无稳定收益，两批留出集偏好相反 |
| 门控阈值 50/60/70 | 平台期，三档同分 |
| 反查词（79 节各补 3 句口语） | 章节命中 +1，小节 @1 −0.05 |

结论：**这个系统的瓶颈不在参数，在架构。** 架构层面还剩下两处没动——数据层（向量库）和生成层（答案正确率）。

### ⑨ 放大到一百万块：先崩的不是延迟，是内存（`bench_scale.py`）

⑧ 的结论是「瓶颈不在参数」。数据层就是下一个要问的地方：**这套暴力检索能撑到多大？**

先说清楚为什么必须用合成数据：本仓库只有 1177 块 × 512 维 = **2.3 MB**，这个规模下 numpy 全量矩阵乘是亚毫秒，换任何索引都测不出差别。「百万级会怎样」在真实语料上永远测不出来。

**合成数据必须对着真实语料标定**，否则测的是生成器的性质。我第一次就错了：簇中心 + 未归一化的噪声，噪声范数 13、簇中心范数 1，结构被噪声盖掉，数据退化成 512 维均匀随机——所有点几乎等距，top-10 取谁全凭数值浮动的运气，HNSW 召回 0.14，衡量的是噪声。

第二版改成低秩子空间，但每簇塞 50 个点，邻域全在簇内、彼此几乎重合，召回直接 1.000，测不出任何权衡。

第三版是现在这个，三项统计贴着真实值：

| 邻域统计 | 真实语料（1177 块） | 合成（每簇 14 点，噪声 0.85） |
|---|---|---|
| top1 相似度 | 0.861 | 0.859 |
| top10 相似度 | 0.786 | 0.793 |
| top1 与 top10 间隔 | 0.075 | 0.066 |
| top10 ±1e-3 内的候选数 | 1.5 | 2.1 |

「每簇 14 点」是被**间隔**钉住的：8 太小（第 10 名跨出簇，间隔 0.378），16 太大（0.034），14 落在真实值附近。

**结果**（512 维、200 条查询、单条计时中位数、8 线程、win11/20 核/16GB）：

| n | numpy 暴力 | faiss 暴力 | HNSW ef=32 | HNSW ef=64 | 加速 | 召回@ef64 | 向量 | 索引 |
|---|---|---|---|---|---|---|---|---|
| 1 万 | 0.26 ms | 0.74 ms | 0.09 ms | 0.13 ms | 2× | 1.000 | 0.02 GB | 0.02 GB |
| 10 万 | 5.33 ms | 7.51 ms | 0.19 ms | 0.33 ms | 16× | 0.994 | 0.19 GB | 0.21 GB |
| 50 万 | 29.79 ms | 75.09 ms | 0.25 ms | 0.43 ms | 70× | 0.995 | 0.95 GB | 1.07 GB |
| 100 万 | 65.41 ms | 149.33 ms | 0.22 ms | 0.32 ms | **206×** | 0.998 | 1.91 GB | 2.15 GB |

四个结论，前三个和直觉不一样：

1. **延迟不是第一道墙。** 100 万块上暴力检索 65 ms/查询，对一个问答场景完全能忍（一次 LLM 调用就是几秒）。HNSW 快 206 倍，但那 65 ms 本来就不是瓶颈。
2. **内存才是。** 100 万块要 1.91 GB 存向量，再加上 HNSW 的图 **2.15 GB——索引比向量本身还大 13%**。合计 4.06 GB，还没算模型和进程开销。想省内存，向量量化（PQ/IVF）比换索引更直接。
3. **构建时间是第二道墙。** 100 万块建 HNSW 要 **196 秒**。这意味着索引不能每次启动重建，必须持久化到磁盘；反过来，用 numpy 暴力检索**零构建成本**，每次启动就是读一个 `.npy`。小语料上这是 numpy 的隐性优势。
4. **换实现不等于更快。** faiss 的 `IndexFlat` 在每一档都比 numpy 慢 2~2.3 倍（149 ms vs 65 ms）。原因不复杂：numpy 的矩阵乘吃满 8 线程，而 faiss 的单条查询只在 1 个线程里跑。**同算法、同复杂度，快慢取决于有没有把机器用满**——这条在面试里比「我用了向量库」值钱得多。

召回这一侧：efSearch=32 就有 0.988~0.995，ef=8 掉到 0.862（10 万）/ 0.783（100 万）。也就是说「召回换延迟」这个旋钮存在，但在这份数据上用不着拧——代价是有近重复的语料才会显出来（本仓库是一本书，块之间区分度高；网络爬取的语料不是）。

**局限**：合成数据没有近重复；查询是单条、单进程；只测了 `IndexHNSWFlat` 一种图索引，没测 IVF-PQ。

### ⑩ 端到端答案正确率：0.925 的检索只换来 0.250 的全中（`eval_answer.py`）

前面所有数字都是**检索**指标。「小节 @3 = 0.950」只说明正确那一节进了前三，**不等于答对**——这条一直写在「已知局限」里，现在把它量出来。

**怎么量**：`answers_43.json` 给 20 题（定义 6 / 细节 6 / 原因 4 / 应用 2 / 分类 1 / 对比 1）各写了 2-4 条**必须出现的事实点**，全部出自原文，附了出处句子供人复核。用「要点制」而不是打分：打分在 20 题上没法解释，0.8 和 0.85 的差别是什么？要点制换个人判也是同一个结果。

**三个指标，一个客观两个主观：**

| 指标 | 值 | 说明 |
|---|---|---|
| 引用命中率（**客观**） | **18/20 = 0.900** | 回答引用的块是否落在正确小节，用 `SUB_MAP` 直查，不调模型 |
| 要点覆盖率 | **33/63 = 0.524** | 命中的事实点 / 全部事实点 |
| 答案全中率 | **5/20 = 0.250** | 所有要点都被明确表达才算对 |
| 拒答 T1 / T2 / T3 | 3/3 · 4/5 · 2/4 | T1 完全离题、T2 同领域但书里没有、T3 书里只提了名字 |
| 拒答 合计 | **9/12 = 0.750** | |

**结论一句话：检索到「小节」的准确率是 0.925，引用落在正确小节的是 0.900，但答案全中只有 0.250。**

**少的那 0.65 去哪了**——15 道没全中的题，逐题看完分三类：

1. **同一小节里，只捞到其中一块（12 题，主因）。** 3.2 有三块，精排挑中的是讲「角色扮演 / 思维链」的那块，而问题问的采样参数在另一块。所以回答是「对的章节 + 错的块」——引用命中判 √，要点判 ×。**这正是 ⑧ 说的「章内选块」，只是这次代价显在生成端。**
2. **生成端过度保守（1 题）。** 13.4 的 MCP 那题，材料就在手里，回答却说「材料里没有相关内容」。
3. **检索就错了（2 题）。** 1.3.3「执行行动循环」被 4.2 的 ReAct 顶掉；9.4 的 NoteTool 被别的块顶掉。

**拒答的三档差距印证了局限 #1**：T1 全对、T2 4/5、T3 只有 2/4。T3 是「书里只提了名字」的问题（「CrewAI 和 AutoGen 该怎么选」），top1 精排分能到 0.969，比不少正样本还高——**相关性分数区分不了「高度相关但没答案」，阈值法在这里是失效的**，只能靠生成端说不知道。

**这份数字的边界**（比数字本身重要）：

- 只做了 20 题。20 题里 1 题 = 5 个点，任何 1 题的差别都不该当结论。
- 判分也是模型。我抽查了 4 题原文，判分与人工判断一致；但换成另一个模型判，结果会有偏移，所以只报比例、不做精调。
- 「全中」这个口径偏严（4 个要点必须全中）。所以我同时报了覆盖率 0.524——**这两个数一起看才有意义**，只报 0.25 会显得系统很糟，只报 0.52 会掩盖「四分之一的问题答不全」。
- 评测中间踩了两个坑，都记在脚本注释里：① 网络抖动会让整轮退出，加了重试；② 模型偶尔返回**空字符串**（不是报错），一题因此被误判成答错，加了空答案重试。**不分清「脚本挂了」和「模型答错」，算出来的正确率就是假的。**

### ⑪ 一个能点开的入口：为什么不是聊天框（`api.py` / `build_demo.py` / `demo.html`）

这个仓库的主张是「小节直选把 @1 从 .700 提到 .950」——**它是关于「找材料」的，不是关于「写答案」的**。所以入口不是一个问答框：

聊天框证明不了这件事。访客问一句、看到一段回答，然后呢？他没看过旧链路的输出，没法判断这段话是变好还是变坏。**能把结论说清的界面，必须同时给出「改之前」和「改之后」。**

所以页面是一个**逐题对照表**：同一道题，左边是旧链路从 79 个章节里选的 3 个，右边是新链路从 287 个小节里选的 3 个，正确的那一节标绿。最上面四行就是被救回来的那几题。

**口径先说清**：两边都复算「最终 top-1 的块落在哪一节」，而不是比「模型选了谁」——旧链路选的是章节、新链路选的是小节，粒度不同，直接比命中率没有可比性。所以页面上的数字和 ⑧ 完全一致：

| 数据集 | 旧：章节路由 | 新：小节直选 | 救回 | 弄坏 |
|---|---|---|---|---|
| h3 干净集（20 题） | 0.700 | **0.950** | 6 | 1 |
| 43 开发集（40 题） | 0.900 | **0.925** | 3 | 2 |

「弄坏 1」也照样列出来。总数是零退化，但**逐题不是**——有救回的也有弄坏的，把它们一起摆出来，比只报总分诚实。

**两个东西，分工不同：**

- `demo.html`（由 `build_demo.py` 生成）：**纯静态、零依赖**，双击就能看，也能挂到任何静态托管。数据来自仓库里的候选池，不加载模型。
- `api.py`：标准库 `http.server`，暴露 `GET /healthz`、`POST /search`，并顺手把 `demo.html` 发出去。页面里的「现场试一句」走它。

**服务只做检索、不做生成**，三个原因：① 不需要把 API key 放进公开实例；② 不会引入「模型编了一段话」这种和 claim 无关的变量；③ 2 秒响应，而不是冷启动 + 生成让人等 60 秒。唯一要 LLM 的是「小节直选」，没配 key 时会降级成纯检索，接口里用 `mode` 字段如实标成 `plain`，不假装。

```bash
python build_demo.py     # 重新生成静态页（不加载模型，1 秒）
python api.py            # http://127.0.0.1:8000
python api.py --no-route # 不调 LLM，只用检索（不需要 key）
```

**在线版**：<https://hugeaaa-asd.github.io/rag-lab/>。静态页挂在 GitHub Pages，源目录是 `docs/`（由 `build_demo.py` 一起生成，和 `demo.html` 同内容）。

在线版只有离线算好的对照数据。「现场试一句」需要后端，Pages 上必然 404——页面对此的文案是「说明分工」，不是报错：在线看数据，想试检索就在本机 `python api.py`。`api.py` 要 500MB 模型和运行环境，没往公有云放（也不想把 key 放上去）。本地已完整验证（`GET /` 200、`/healthz` 报 `chunks: 1177`、路由模式命中 7.4.1 SimpleAgent，精排 0.9694）。

## 已知局限

写出来是因为它比上面的数字更重要。

1. **T3 型问题阈值法救不了。** 「CrewAI 和 AutoGen 该怎么选」top1 拿到 0.969，比不少正样本还高。相关性分数根本无法区分「高度相关但没答案」和「有答案」。真要解决这个问题，靠的是**生成端说不知道**，不是检索端卡阈值——所以 `answer.py` 里除了阈值，还有一条「材料里没有就说不知道」的宪法规则兜底。
2. **43 题样本量偏小。** 尤其是分类、对比两类各 2 题，数字仅供参考，不能用来做性能承诺。结论只能说「在这 43 题上」，不宜外推。
3. **检索指标会高估系统能力，⑩ 已经量出来了。** 小节 @3 = 0.950，但 20 题上答案全中只有 0.250、要点覆盖 0.524。差的那 0.65 主要是「同一小节里只捞到其中一块」——检索停在「小节对了」，生成却需要「块对了」。
4. **每题 12~20 秒，离上线很远。** 本地 cross-encoder + 串行改写，没有并发、没有缓存命中率优化、没有向量库（用的是 `numpy` 全量 `.npy` 暴力遍历，1177 块 × 512 维直接矩阵乘）。放大到百万级会怎样，⑨ 是量过的：**先崩在内存**（4.1 GB，其中索引 2.15 GB 比向量还大），延迟 65 ms 反而不是问题。
5. **依赖 `rewrites.json` 做改写缓存**，同一个问题第二次问才会命中。
6. **同一配置重复跑会差一题。** 路由调 LLM，判别有非确定性；43 题里一题就是 2.3 个点。上面所有 1~2 题的差异都要当成噪声看，不能用来说明某个改动的收益。真要比较，得跑 3 次取中位数，或者把路由结果缓存下来做固定对照——后者已经做了（`allsub_pools_*.json`），这也是 `reproduce.py` 能复现的原因。
7. **h3 还有 1 道错题没修。** 「敲命令查出来的东西怎么存进记忆」→ 模型选了 8.2 记忆系统，答案是 9.5.4 文件系统。纯语义混淆。**不修的理由**：h3 只有 20 题，1 题就是 5 个点，照着它改词就是过拟合；写进局限比修掉更有价值。
